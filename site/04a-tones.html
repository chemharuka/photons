4.1–4.6 影调：白平衡、曝光、端点、对比、曲线

第 3 章说参数该待在哪个域。这一章给算式：白平衡、曝光、三个影调窗口、两个端点、对比、曲线。每一节按同一结构写——解决什么问题、算式、参数、实现、开源对照、已知取舍。

常数一律抄自 Sources/PhotonsCore/Kernels/，范围与默认值一律抄自 Sources/PhotonsCore/EditModel.swift。两者冲突时以 kernel 为准，冲突本身在哪一节都会点名。

4.1 白平衡、色调与黑电平

它解决什么问题

把「这张图的光是什么颜色」定下来，再把用户想要的偏移叠上去。白平衡决定中性色落在哪，色调（tint）修绿/品红偏移，黑电平决定「0」在哪。三者的共同要求是：没碰过时必须逐字节不变。

算法

白平衡是解码参数：文档里的 (K, tint) 写回 CIRAWFilter.neutralTemperature/neutralTint，解码器据此出图（Sources/PhotonsCore/EditModel.swift:1284）。拖拽期间为了实时，另用本节这套场景线性估计给出等效增益预览——下面算的是估计器，不是解码器的模型。请求先落成 CIE 1960 uv 上的一个点：普朗克轨迹用 Kim 的解析拟合，并把 6500 K 平移到位，使它与工作白 D65 重合（Sources/PhotonsCore/WhiteBalanceEstimate.swift:240）；tint 沿轨迹法线位移，幅度 5×10−55\times10^{-5} uv/单位（Sources/PhotonsCore/WhiteBalanceEstimate.swift:287）。uv → XYZ 后做 Bradford 适应到工作白，得到 3×3 矩阵（Sources/PhotonsCore/WhiteBalanceEstimate.swift:349），但过 CPU/GPU 边界的不是矩阵，是三个归一化通道数。

记 W(T)W(T) 为求解器在温度 TT 给出的线性白光，Tref,τrefT_{\text{ref}},\tau_{\text{ref}} 为参考对，则增益是通道比、绿归一：

r=Wr(Tref)Wr(T),g=Wg(Tref)Wg(T),b=Wb(Tref)Wb(T),(r,g,b)←(rg,1,bg)r=\frac{W_r(T_{\text{ref}})}{W_r(T)},\quad g=\frac{W_g(T_{\text{ref}})}{W_g(T)},\quad b=\frac{W_b(T_{\text{ref}})}{W_b(T)},\qquad (r,g,b)\leftarrow\left(\frac{r}{g},\,1,\,\frac{b}{g}\right)

色调是编码域上的二次项，转到线性域就是一次乘与一次开方：

s=(1+τ−τref600)2,g←gs,r←sr,b←sbs=\left(1+\frac{\tau-\tau_{\text{ref}}}{600}\right)^{2},\qquad g\leftarrow \frac{g}{s},\quad r\leftarrow \sqrt{s}\,r,\quad b\leftarrow \sqrt{s}\,b

参考对不写死成 6500 K / 0。先从解码缓冲估出画面自己的照度：三个估计器（白块 p99.5、1 %–99 % 截尾的灰世界均值、梯度加权的灰边）各给一个答案，逐通道取中位数（Sources/PhotonsCore/WhiteBalanceEstimate.swift:91、Sources/PhotonsCore/WhiteBalanceEstimate.swift:98）；测出的色度 ≤ 0.02 时退回名义值（Sources/PhotonsCore/WhiteBalanceEstimate.swift:364）。所以「as shot」与「显式 6500 K」在已平衡的画面上互为恒等，而偏色画面上的请求是相对它自己的偏色。

黑电平是加法，且在增益之前：

v←v+o,o=blackOffset∈[−0.01,+0.01]v \leftarrow v+o,\qquad o=\text{blackOffset}\in[-0.01,\,+0.01]

位置是 071 定的：加法量要被同一个增益缩放，负样本才和正样本一起被抬过零（Sources/PhotonsCore/Kernels/s1_scene_linear.metal:237）。

实现

预览路径上，GPU 侧只有一行：v *= p.a.x * p.a.yzw（Sources/PhotonsCore/Kernels/s1_scene_linear.metal:245），a 的四个分量就是曝光增益与 wbR/wbG/wbB（Sources/PhotonsCore/Kernels/s1_scene_linear.metal:150）。as shot（不写回、也不加增益）时三个数是字面量 1（Sources/PhotonsCore/RenderGraph.swift:3371）；「未改动」还要求 blackOffset == 0 等条件同时成立，才走整段拷贝的分支（Sources/PhotonsCore/RenderGraph.swift:3376）。照度估计在 CPU、每个缓冲一次并缓存（Sources/PhotonsCore/RenderGraph.swift:1548），GPU 只拿到三个数——没有矩阵、没有查表。

开源对照

  • darktable temperature（src/iop/temperature.c）：系数来自相机矩阵与按文件记录的照度选表，是「查表 + 相机模型」；本实现是在解码后的线性缓冲上自己估照度再算增益——https://github.com/darktable-org/darktable/blob/master/src/iop/temperature.c
  • RawTherapee 的 RAW 阶段白平衡（rtengine/rawimagesource.cc）：乘子乘在去马赛克之前的马赛克上，以 refwb_* 的 as-shot 为参考；本实现乘在已去马赛克的线性图上，参考来自画面估计而不是文件记录——https://github.com/Beep6581/RawTherapee/blob/dev/rtengine/rawimagesource.cc

取舍

  • 估计是抽样的：至多 12 万像素、确定性步长（Sources/PhotonsCore/WhiteBalanceEstimate.swift:118）。一张大面积单色的画面，三个估计器会一起错。
  • 增益夹在 1/20…20（Sources/PhotonsCore/WhiteBalanceEstimate.swift:420），极端请求在这个边界上饱和，而不是报错。
  • LightGroup.whiteBalanceGains 还留着，但它是编码域拟合、约弱 2.2 倍，管线不用它（Sources/PhotonsCore/EditModel.swift:1446）。读代码的人容易把它当成实现。
  • 预览与落定的关系：预览是增益、落定是解码器的模型，两者不承诺逐像素相同；一致的是请求的白点，不是实现。143 暂时删掉了写回，所以当前 main 上落定也走增益——核对清楚后再定这条取舍怎么写。

4.2 曝光

它解决什么问题

给整幅画面加减光。它必须是一次纯增益，必须在任何压缩之前完成——一旦压在显示域，被压掉的高光就再拿不回来。它也是 S1 里唯一不带窗口的增益：不改斜率、不改色度、不动任何端点。

算法

v←v⋅2Ev \leftarrow v\cdot 2^{E}

EE 是文档的 EV。没有夹取、没有端点、没有曲线参与（Sources/PhotonsCore/Kernels/s1_scene_linear.metal:245）。位置固定：在加法微调之后、两个端点之前（Sources/PhotonsCore/Kernels/s1_scene_linear.metal:239、Sources/PhotonsCore/Kernels/s1_scene_linear.metal:251）。

有一条配套约定让曝光可交换：whites 的窗口读「没加曝光的亮度」L0L_0，而不是画面当前的 LL：

L0=L−log⁡22EL_0=L-\log_2 2^{E}

（Sources/PhotonsCore/Kernels/tone_shape.metal:233。）于是曝光平移画面、不平移窗口，同一个 whites 数值在 E0 与 E+2 下作用在同一批场景影调上（Sources/PhotonsCore/Kernels/tone_shape.metal:207）。

参数与范围

参数 范围 默认 单位
exposure −5…+5 0 EV（Sources/PhotonsCore/EditModel.swift:1245）
增益 2^E 1/32…32 1 倍（Sources/PhotonsCore/EditModel.swift:1437）

实现

增益在 CPU 上算：exposureGain = pow(2, exposure)（Sources/PhotonsCore/EditModel.swift:1437），作为 S1Params.a.x 传入（Sources/PhotonsCore/RenderGraph.swift:3388）。只有 kKnee 打开时，它才额外作为参数交给端点函数（Sources/PhotonsCore/Kernels/s1_scene_linear.metal:257），因为 L0L_0 要用到它；g = 1 时 L0=LL_0=L 逐位成立（Sources/PhotonsCore/Kernels/tone_shape.metal:212）。

高光恢复在同一次 dispatch 的最后：膝 0.8，amount=0 是精确恒等，amount=1 渐近 1.0（Sources/PhotonsCore/Kernels/s1_scene_linear.metal:262）。它永远排在端点之后——whites 说白点在哪，恢复说肩怎么压（Sources/PhotonsCore/Kernels/s1_scene_linear.metal:139）。

开源对照

  • darktable exposure（src/iop/exposure.c）：同一模块里还有黑点与 deflicker，且黑点被约束在白点之下；本实现的曝光只有一个数，黑电平是另一个加法量、在增益之前——https://github.com/darktable-org/darktable/blob/master/src/iop/exposure.c
  • darktable filmicrgb（src/iop/filmicrgb.c）：那里「曝光」是相对曝光的范围归一化，先定白/黑相对 EV 再上曲线；本实现的曝光是乘在光上的纯增益，范围由 whites 的 EV 窗口另行表达——https://github.com/darktable-org/darktable/blob/master/src/iop/filmicrgb.c

取舍

  • kernel 不夹取 p.a.x。−5…+5 只是文档声明的范围（Sources/PhotonsCore/EditModel.swift:1245），手改文档能超出滑杆。
  • 高光恢复吃的是 S1 出口的值，也就是已经过 blacks/whites 的值；想把肩放在端点之前，目前没有位置。

4.3 高光、中间调、阴影

它解决什么问题

三个滑杆分别抬或压暗部、中间调、亮部。判据是两条：每个亮度都必须有主人（中间不能有死带），而一个滑杆在作用自己的区段时还要带动邻居——用户的口径是「中间调调节以中间区域为主，但也能带动阴影和高光。其他的也类似，避免局部对比度的损失」。085 的两条互补 smoothstep 链是互斥的：相邻控件带动严格为 0，单拉中间调时窗口缝隙上的输出斜率只有 0.30。306 把权重换成三个归一化重叠高斯。

算法

坐标仍是 L=log⁡2YL=\log_2 Y（相对显示白的 EV，直方图自己的轴）。三个中心坐在参考帧的阴影 / 中位 / 高光上，宽度 1.9 EV：

cs=−6.8,cm=−3.6,ch=+0.2EV,σ=1.9EVc_s=-6.8,\quad c_m=-3.6,\quad c_h=+0.2\ \text{EV},\qquad \sigma=1.9\ \text{EV}

bi=exp⁡(−((L−ci)/σ)22),wi=bi∑jbj⇒∑iwi≡1b_i=\exp\!\left(-\frac{((L-c_i)/\sigma)^2}{2}\right),\qquad w_i=\frac{b_i}{\sum_j b_j}\qquad\Longrightarrow\qquad \sum_i w_i\equiv 1

归一化是硬条件，不是装饰：不归一的高斯（darktable toneequal 的老路）在相邻区会出现反号瓣；凸组合则永远落在三个滑杆值之间，不会振铃。权重是 C∞C^\infty、全轴支撑，所以每个控件都能带动另外两个。中档峰值权重 0.726（L=−3.6L=-3.6），另两档中心看到的中间调权重是 0.195 / 0.119。全局增益是

v←v⋅2wsds+wmdm+whdh+S(L)v\leftarrow v\cdot 2^{\,w_s d_s+w_m d_m+w_h d_h+S(L)}

ds,dm,dhd_s,d_m,d_h 是已经过门的 EV 位移。306b 把高光也放进凸组合：L=0L=0 处 wh=0.856w_h=0.856，所以白点附近的 SDR 也跟高光走（h=−100h=-100 时 L=0L=0 动 −0.71-0.71 EV），这就是「其他的也类似」。权重直接用 LL，不在白点冻结：L→+∞L\to+\infty 时 wh→1w_h\to1，band 项趋于常数 dhd_h；299 的 HDR 尾由差额肩 SS 补足（下面）。蒙版路径（s1_6_local）仍用 074 的两窗口和第三个 EV 行程。

行程重标定。 高斯峰值是 0.726，若沿用旧行程（0.90 / 0.70 / 0.60），每个档位中心的实际位移会掉 27 %。所以满行程乘 1/0.726=1.3781/0.726=1.378：

Δs=1.24,Δm=0.96,Δh=0.83EV\Delta_s=1.24,\qquad \Delta_m=0.96,\qquad \Delta_h=0.83\ \text{EV}

单拉中间调时，阴影中心（−6.8 EV）被动抬 0.195⋅0.96=+0.1870.195\cdot0.96=+0.187 EV，高光中心（+0.2 EV）被动抬 0.119⋅0.96=+0.1150.119\cdot0.96=+0.115 EV；L=0L=0 处的中间调权重是 0.143（「以中间为主」）。

单调性门。 归一化不保证 d(out)/dLd(\text{out})/dL 不折；门把精确判据放在 CPU：

d(log⁡2v′)dL=1+∑iwi′(L)Δi\frac{d(\log_2 v')}{dL}=1+\sum_i w_i'(L)\,\Delta_i

在 L∈[−12,0]L\in[-12,0]、步长 0.05 EV 上取最小值；低于 minSlope = 0.500 时才按 scale = (1 − minSlope)/(1 − min) 等比压缩三个 Δ\Delta。默认行程下实测最坏 0.5287（L=−5.35L=-5.35，+1.24/−0.96/+0.83+1.24/-0.96/+0.83 的反号角），门从不触发；单个滑杆的斜率地板是阴影 0.717、中间调 0.765、高光 0.774（高光进了 band，不再是 1.000）。085 的 0.30 因此成为历史。

实现

kernel 做归一化高斯的三个权重、dot(w, d)、high_shoulder_ev 差额肩和一次 exp2（Sources/PhotonsCore/Kernels/tone_shape.metal、s2_tone_map.metal）；行程、斜率 kk 与单调性门都在 CPU（S2Regions.weights / travelEV / highSlopeCoefficient / highSlope / highShoulderEV）——kernel 收到的是三个 EV 与 kk，不是滑杆位置。“图不会折”因此是一个可计算的属性，而不是窗口宽度选得巧。蒙版路径用 S2Regions.maskTravelEV 保留 074 的旧数值，s1_6_local 的像素不动。

S2 在入口不夹取：v = c.rgb 直接进权重（Sources/PhotonsCore/Kernels/s2_tone_map.metal:81），只在本阶段末尾取 max(v, 0)（Sources/PhotonsCore/Kernels/s2_tone_map.metal:99）。原因是解码器会给零以下的样本，抬升已把它们拉过零的像素是真画面。alpha 0 与内容矩形两道守卫在像素运算之前（Sources/PhotonsCore/Kernels/s2_tone_map.metal:64、s2_tone_map.metal:71），否则抬暗部会把黑边一起点亮。

开源对照

  • darktable toneequal（src/iop/toneequal.c）：场景线性相机 RGB 上的八度高斯权重 + 线性解法；它不归一化，所以相邻区会有反号瓣。本实现是显示参考域的三个归一化高斯，没有空间项、没有解法——https://github.com/darktable-org/darktable/blob/master/src/iop/toneequal.c
  • RawTherapee / ART 的 shadows/highlights：固定分母的钟形权重（∑g(0)=1.7726\sum g(0)=1.7726），凸组合因此不振铃；本实现的分母是逐像素精确的 ∑bi\sum b_i，所以 ∑w≡1\sum w\equiv1 是浮点事实而不是常数近似——https://github.com/Beep6581/RawTherapee/blob/dev/rtengine/ipshadowshighlights.cc
  • LightZone 的分割 B 样条（Spline.java）：用精确的单位分割保证各段权重和恒为 1；本实现用高斯做同一件事，换来 C∞C^\infty 和全轴支撑。

取舍

  • 单个 shadows +100 / midtones +100 / highlights +100 的满行程 1.24 / 0.96 / 0.83 EV 在中心成立，但接缝上的局部斜率会降到 0.717 / 0.765 / 0.774（085 是 0.30）；派单里 0.80 的数字是用重标定前的 0.90 / 0.70 / 0.60 行程测的，那时是 0.795 / 0.828 / 0.836。若要同时保住中心行程和 0.80 地板，需要更大的 σ\sigma 或更远的中心，二者都会改变用户已经认可的区段位置。
  • 高光进了 band，但在 σ=1.9\sigma=1.9 的归一化三高斯里，它对阴影中心的带动只有 0.00075 EV（对中间调中心是 0.0815 EV）。要让高光把阴影中心抬到 0.03 EV 需要 σ≈2.8\sigma\approx2.8，而那时中间调对阴影的带动会变成 0.447，破坏验收 2 的 0.187±0.02 和「以中间为主」。这是一个有意的取舍，不是漏项。
  • L=+8L=+8、h=−100h=-100 的输出从 299 的 1.798 EV 变成 2.681 EV：高光现在先作为 band 压 SDR 近白，肩只补差额；旧数字依赖「高光不进 band」，无法同时保留。
  • 蒙版内的阴影/高光仍用 074 的两窗口 region_weights / region_weights3（Sources/PhotonsCore/Kernels/tone_shape.metal），与全局的三段故意不同步。同一次拖动，全局与蒙版的响应因此不完全同形，等「两套体统一」的单独任务。
  • 权重中心与宽度是固定常数，不随画幅、不随内容自适应；动态范围很窄的图会整幅落在同一组权重上，三个滑杆于是都动它。

4.4 白点与黑点

它解决什么问题

把最暗与最亮钉在哪。纯乘法做不到：0 → 0 对任何增益都成立，所以黑点既压不到 0 也浮不起来；纯加法会造灰。答案是「EV 膝 + 电平」的混合，两半按行程混合。

算法

记 t=blacks/100t=\text{blacks}/100，a=|t|a=|t|，LL 是端点的坐标（BT.709 亮度取对数）：

wb=1−ss(−12,−1,L),v←v⋅23.0twbw_b=1-\mathrm{ss}(-12,-1,L),\qquad v\leftarrow v\cdot 2^{3.0\,t\,w_b}

这就是前半段，也是整个 |t|≤0.2|t|\le 0.2 时的全部算术（Sources/PhotonsCore/Kernels/tone_shape.metal:237、Sources/PhotonsCore/Kernels/tone_shape.metal:267）。超过 0.2 之后电平进场：

m=ss(0.2,1,a),wl=1−ss(−6,−1,L),off=0.006tmwlm=\mathrm{ss}(0.2,1,a),\qquad w_l=1-\mathrm{ss}(-6,-1,L),\qquad \text{off}=0.006\,t\,m\,w_l

off<0:v←T(v+off)⋅g,off>0:v←T(v⋅g+off),g=23.0twb\text{off}<0:\ v\leftarrow T(v+\text{off})\cdot g,\qquad \text{off}>0:\ v\leftarrow T(v\cdot g+\text{off}),\qquad g=2^{3.0\,t\,w_b}

（Sources/PhotonsCore/Kernels/tone_shape.metal:245、Sources/PhotonsCore/Kernels/tone_shape.metal:250、Sources/PhotonsCore/Kernels/tone_shape.metal:262。）顺序看符号，这是单调性的来源：压暗时两件事都变暗，先电平后增益；提亮时电平必须骑在增益外面，否则 ±0.006 在 8× 增益里会被放大八倍，最暗的那一格反而最亮（Sources/PhotonsCore/Kernels/tone_shape.metal:254）。

TT 是 C¹ 整流器，膝 k=10−3k=10^{-3}：

T(x)={x,x≥k0,x≤−k(x+k)24k,otherwiseT(x)=\begin{cases}x, & x\ge k\\ 0, & x\le -k\\ \dfrac{(x+k)^2}{4k}, & \text{otherwise}\end{cases}

（Sources/PhotonsCore/Kernels/tone_shape.metal:186。）压暗一侧真的会到 0——那就是「改电平」的意思；提亮一侧 off ≥ 0 不夹取，所以 t=+1 不会把正的样本压到 0。

白点用同一个函数的后半段，但读 L0L_0：

u=whites100,ww=ss(−2,2,L0),λ=11−0.20u|u|,v←v⋅21.2uww⋅λu=\frac{\text{whites}}{100},\qquad w_w=\mathrm{ss}(-2,2,L_0),\qquad \lambda=\frac{1}{1-0.20\,u\,|u|},\qquad v\leftarrow v\cdot 2^{1.2\,u\,w_w}\cdot\lambda

（Sources/PhotonsCore/Kernels/tone_shape.metal:275、Sources/PhotonsCore/Kernels/tone_shape.metal:276。）λ\lambda 是乘法电平、没有窗口，所以它缩放每一档亮度（含 HDR 尾）；u=0u=0 时 λ=1\lambda=1，中性文档逐字节不变（Sources/PhotonsCore/Kernels/s1_scene_linear.metal:113）。

4.5 全局对比度

它解决什么问题

让局部反差变大，同时不动整体亮度。乘一个幂律斜率做不到这件事：它把中间调一起推上顶，细节与整体分不开。还有一条硬条件——它必须与曝光可交换：先加曝光再加对比，与先对比再加曝光，必须是同一张图。

算法

只分解亮度 YY（显示参考、白 = 1 = 0 EV），一切增益都是残差，没有绝对锚点：

Y=max⁡(⟨max⁡(rgb,0)⟩w,10−6),G=log⁡2YY=\max(\langle\max(\mathrm{rgb},0)\rangle_w,\,10^{-6}),\qquad G=\log_2 Y

Bc=GF(G;rc,εc),D1=G−Bc,Bm=GF(D1;rm,εm),Df=D1−BmB_c=\mathrm{GF}(G;r_c,\varepsilon_c),\quad D_1=G-B_c,\quad B_m=\mathrm{GF}(D_1;r_m,\varepsilon_m),\quad D_f=D_1-B_m

G′=G+γ(kmBm+kfDf),rgb′=max⁡(rgb,0)⋅2G′−GG'=G+\gamma\left(k_mB_m+k_fD_f\right),\qquad \mathrm{rgb}'=\max(\mathrm{rgb},0)\cdot 2^{G'-G}

（Sources/PhotonsCore/Kernels/s1_8_contrast.metal:17。）GF\mathrm{GF} 是自引导滤波，a=var/(var+ε)a=\mathrm{var}/(\mathrm{var}+\varepsilon)、b=I‾(1−a)b=\bar I(1-a)（Sources/PhotonsCore/Kernels/s1_8_contrast.metal:266）。γ\gamma 是梯度门，读的是窗口均值的梯度：

γ=1−ss(0.05,2.00,|∇D‾1|)\gamma=1-\mathrm{ss}(0.05,\,2.00,\,|\nabla \bar D_1|)

（Sources/PhotonsCore/Kernels/s1_8_contrast.metal:274。）门只乘两条细节带，所以强边附近不会被放大成晕。

权重两段不同律（Sources/PhotonsCore/Kernels/s1_8_contrast.metal:300）：

t≥0:km=7.50t,kf=3.75t;t<0:km=kf=20.75t−1t\ge 0:\ k_m=7.50\,t,\ k_f=3.75\,t;\qquad t<0:\ k_m=k_f=2^{0.75t}-1

负向是收缩，不是反号的行程：残差最小乘到 0.59，恒为正（Sources/PhotonsCore/ContrastMultiscale.swift:184）。正向到白点要淡出，并给一个上限：

d>0:d←d(1−ss(−1,0,G)),G<log⁡20.98⇒d≤log⁡20.98−Gd>0:\quad d\leftarrow d\left(1-\mathrm{ss}(-1,0,G)\right),\qquad G<\log_2 0.98\ \Rightarrow\ d\le\log_2 0.98-G

（Sources/PhotonsCore/Kernels/s1_8_contrast.metal:327。）所以白点以下没有像素能被推上顶；而已经大于 1 的 HDR 样本照常扩张（Sources/PhotonsCore/Kernels/s1_8_contrast.metal:329）。黑地板 0.00110 保证「清过地板」的像素不会被压到地板以下（Sources/PhotonsCore/Kernels/s1_8_contrast.metal:341）。

实现

统计不在全分辨率上做。系数图在长边 1024 的整幅代理上建一次并缓存（Sources/PhotonsCore/ContrastMultiscale.swift:115、Sources/PhotonsCore/RenderGraph.swift:3732），所以适应、25 %、1:1、平移中的 1:1 窗口取样的是同一张图——一个物理像素的增益不能取决于窗口在哪。kernel 分五个 pass：pack（每 q×qq\times q 块写均值与平方均值）→ 水平盒 → 垂直盒 → 系数 → apply，带蒙版时 apply 换成 masked 变体。

  • 负向只能把残差压到 0.59×，永远不是 0：2^t 会把画面均值拉走 −1.21 码，超出「±1 码」的预算，所以取了 0.75（Sources/PhotonsCore/Kernels/s1_8_contrast.metal:306）。

  • 系数图固定 1024 长边：画面小于 1024 时它就是自己（逐位复用旧系数），大于它时 1:1 拿到的是上采样结果（Sources/PhotonsCore/ContrastMultiscale.swift:105）。

4.6 HDR 曲线

它解决什么问题

一条曲线，要同时弯 SDR 的 0–255 与显示白以上的 +0…+4 EV，而且必须与它上面的直方图同轴——左半是显示码，右半是 stops。它是管线里唯一一个用户直接画形状的算子：不解释画面，只执行点列。

算法

横轴 uu 是分段函数，SDR 半边用 sRGB 编码，HDR 半边用 log⁡2\log_2：

u(x)={0.5sRGB(x),0<x≤10.5+0.125log⁡2x,x>1x(u)={sRGB−1(2u),u≤0.528(u−0.5),u>0.5u(x)=\begin{cases}0.5\,\mathrm{sRGB}(x), & 0<x\le 1\\ 0.5+0.125\log_2 x, & x>1\end{cases} \qquad x(u)=\begin{cases}\mathrm{sRGB}^{-1}(2u), & u\le 0.5\\ 2^{8(u-0.5)}, & u>0.5\end{cases}

（Sources/PhotonsCore/Kernels/s1_7_hdr_curve.metal:15。）于是 u(0.18)=0.2307u(0.18)=0.2307、u(1)=0.5u(1)=0.5、u(4)=0.75u(4)=0.75、u(16)=1u(16)=1（Sources/PhotonsCore/Kernels/s1_7_hdr_curve.metal:20）。白点位置 0.50.5 与每档宽度 0.1250.125 都从 uniform 来，不写死在 kernel 里（Sources/PhotonsCore/Kernels/s1_7_hdr_curve.metal:109），CPU 的参考实现与 GPU 的整形器因此不可能漂移。

表里存的是 v∈[0,1]v\in[0,1]，插值在 uu 上做（Sources/PhotonsCore/Kernels/s1_7_hdr_curve.metal:126）。W 曲线是亮度增益，不是逐通道查表：

v←v⋅2Δ,Δ=clamp(log⁡2x(v)x(u),−12,+12)v\leftarrow v\cdot 2^{\Delta},\qquad \Delta=\mathrm{clamp}\left(\log_2\frac{x(v)}{x(u)},\,-12,\,+12\right)

（Sources/PhotonsCore/Kernels/s1_7_hdr_curve.metal:237。）Δ\Delta 是两束光的比，不是 uu 差乘常数——SDR 半边上 1 个 uu 是 12–100 个 stops，乘常数会让中间调弱 40 %（Sources/PhotonsCore/Kernels/s1_7_hdr_curve.metal:231）。R/G/B 是可分表，各自独立：

vc←x(LUTc(u(vc))+max(u−1,0)⋅clamp(sc,−2,2))v_c\leftarrow x\left(\mathrm{LUT}_c\big(u(v_c)\big)+\max(u-1,0)\cdot\mathrm{clamp}(s_c,-2,2)\right)

（Sources/PhotonsCore/Kernels/s1_7_hdr_curve.metal:180、Sources/PhotonsCore/Kernels/s1_7_hdr_curve.metal:243。）顺序 W → R → G → B：先整幅影调，再偏色（Sources/PhotonsCore/Kernels/s1_7_hdr_curve.metal:94）。

四条边界规则都不 Optional：① 恒等表直接拷贝（Sources/PhotonsCore/Kernels/s1_7_hdr_curve.metal:192）；② alpha 0 与内容矩形的守卫（Sources/PhotonsCore/Kernels/s1_7_hdr_curve.metal:198、Sources/PhotonsCore/Kernels/s1_7_hdr_curve.metal:205）；③ x≤0x\le0 原样穿过、保号，除非黑点被抬过（此时落进表的常值段，负样本一起被夹）（Sources/PhotonsCore/Kernels/s1_7_hdr_curve.metal:175）；④ u>1u>1 按末段斜率继续，不夹取（Sources/PhotonsCore/Kernels/s1_7_hdr_curve.metal:180）。

取舍

  • W 曲线永远不会被反相：下降的 W 点列到了 kernel 就是恒等表（Sources/PhotonsCore/Kernels/s1_7_hdr_curve.metal:97）。负片的下降只能交给 R/G/B 三张表，它们各自可以整体下降（Sources/PhotonsCore/Kernels/s1_7_hdr_curve.metal:99）。
  • u>1u>1 是线性外推，一段之外没有第二道形状；斜率夹在 ±2 是防手改文档，不是画面决定（Sources/PhotonsCore/Kernels/s1_7_hdr_curve.metal:71）。
  • Δ\Delta 夹在 ±12 EV 是 fp16 保护：把白点从 0.5 拖到 1.0 是 +9 EV，200 级的像素在 half float 里已经接近 inf（Sources/PhotonsCore/Kernels/s1_7_hdr_curve.metal:235、Sources/PhotonsCore/Kernels/s1_7_hdr_curve.metal:238）。所以极端的点列会被截断，而且不会有提示。

曲线之后，S2 交出 0…1，S2.5 的对比与 S3 的色彩才有可用的坐标。这六节加起来只说明一件事：每个滑杆都待在自己的域里，而且都能被一行算式复述。
