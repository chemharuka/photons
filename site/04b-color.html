4.7–4.9 色彩：饱和、色带、分级

这三节一共五个 pass，四种互补的选择器：S3 按「全体像素」选，S3.6 按「色相」选，S3.6b 按「一个采样色附近的一块区域」选，S3.8 按「亮度」选；S3.4 是 S3.6 的灰度版，共用后者的色带。五个 pass 全跑在显示参考域，位置在 S2.5 之后（Stage.swift:190–:196）。它们之间没有共享算式，只有两份共享定义：color_hsl.metal 的 RGB↔︎HSL（S3 与 S3.5），oklch_bands.metal 的 OKLCh 与八色带几何（S3.6 与 S3.4）。

判据还是第 3 章那一句：对象是「显示出来的样子」，就得待在显示域。

4.7 自然饱和度与饱和度（S3）

它解决什么问题

一条全局饱和对「已经很鲜艳」和「刚有一点颜色」的像素一视同仁：+30 把正红顶到夹位（ss 夹在 1），一片灰蓝天却几乎不动。自然饱和度要的是相反的加权：离灰越近的像素动得越多，已经饱和的像素不动。所以这两条滑杆得是两个算子，不能是一条滑杆挂两个名字。

算法

先把像素读成 HSL（color_hsl.metal:21–:39）：

mx=max⁡(r,g,b),mn=min⁡(r,g,b),l=12(mx+mn)m_x=\max(r,g,b),\qquad m_n=\min(r,g,b),\qquad l=\tfrac12(m_x+m_n)

s={d/(2−mx−mn),l>0.5d/(mx+mn),otherwise,d=mx−mns=\begin{cases} d/(2-m_x-m_n), & l>0.5\\ d/(m_x+m_n), & \mathrm{otherwise}\end{cases},\qquad d=m_x-m_n

也就是说 s=d/(1−|2l−1|)s=d/(1-\lvert 2l-1\rvert)，一个纯粹由显示码算出的「距灰多远」，跟亮度无关，跟感知也无关（color_hsl.metal:29）。

自然饱和度是加性的，按剩余空间加权，vv 是滑杆值：

s1=clamp(s+v100⋅12(1−s),0,1)s_1=\mathrm{clamp}\Bigl(s+\frac{v}{100}\cdot\tfrac12\,(1-s),\ 0,\ 1\Bigr)

饱和是乘性的，uu 是滑杆值。两条依次施加，先自然饱和再饱和（s3_color.metal:73–:78）：

s2=clamp(s1(1+u/100),0,1)s_2=\mathrm{clamp}\bigl(s_1\,(1+u/100),\ 0,\ 1\bigr)

12\tfrac12 是斜率，不是可调参数：v=+100v=+100 把 s=0.5s=0.5 的像素送到 0.750.75，s=0.9s=0.9 的送到 0.950.95，s=0s=0（灰）恒为 0。自然饱和度对灰色没有任何作用，这是算术事实。u=+100u=+100 把距离翻倍，−100-100 得到纯灰。

HDR 余量绕着 HSL 走，不穿过它：先按峰值归一，再进 HSL，出来再乘回去（s3_color.metal:66–:68、:81）：

k=max⁡(1,p0.9),p=max⁡(r,g,b),out=k⋅hsl2rgb(s2,l,h)k=\max\Bigl(1,\ \frac{p}{0.9}\Bigr),\qquad p=\max(r,g,b),\qquad \mathrm{out}=k\cdot\mathrm{hsl2rgb}(s_2,\,l,\,h)

目标是 0.9 而不是 1.0，因为 rgb_to_hsl 对峰值恰好为 1 的颜色恒返回 s=1s=1（s=(1−mn)/(1−mn)s=(1-m_n)/(1-m_n)），那样饱和滑杆在任何 HDR 像素上都是空操作（:62–:65）。归一化保住色度比例，+ 方向就还有行程。

参数与范围

参数 范围 默认 单位 出处
vibrance −100…100 0 滑杆单位（÷100 进公式，斜率 1/2） EditModel.swift:2292
saturation −100…100 0 滑杆单位（÷100 = 乘性系数 − 1） EditModel.swift:2063

两个都为 0 时，CPU 侧把身份位置 1：S3 仍在链上（它是无条件 pass），但整段直写（s3_color.metal:24、:33）。身份位只看这两个数（RenderGraph.swift:4114–:4116）。

实现

Kernels/s3_color.metal，一个全分辨率 pass，三处早退：身份位（:33）、alpha 为 0 的黑边（:43）、内容矩形之外（:50）。后两处守的是「matte 不是阴影」：S0 用 alpha 0 标记「这里没有照片」，否则一次提黑会把黑边一起提亮。

HSL 的算式不在这份文件里，在 color_hsl.metal，由 S3 与 S3.5 各自 include（s3_color.metal:21、color_hsl.metal:78–:81）。这是 056 的硬要求：一张全画布蒙版在饱和 +40 上必须与全局滑杆 +40 得到同一张图，不是「看起来差不多」。

开源对照

  • darktable · colorbalancergb.c 的 global vibrance：同一件事的另一种写法，增益是 v(1−C|v|)v\,(1-C^{\lvert v\rvert})，CC 是 Filmlight Ych 的彩度，再并进一个总的 chroma_factor（https://github.com/darktable-org/darktable/blob/master/src/iop/colorbalancergb.c，第 718–719 行）。差别在权重函数和空间：darktable 的指数随滑杆值变，Photons 的斜率恒为 1/2；darktable 在 Ych，Photons 在 HSL 饱和上。
  • darktable · vibrance.c：这个独立模块已被标为弃用，模块提示让用户改用 color balance rgb 里的 vibrance 滑杆（https://github.com/darktable-org/darktable/blob/master/src/iop/vibrance.c，第 59 行）。Photons 保留独立 pass 是为了共享算式，跟沿革无关。
  • RawTherapee · ipvibrance.cc：ImProcFunctions::vibrance 工作在 LabImage 上，用 pastel / saturated 两个阈值区加一条肤色保护曲线（https://github.com/RawTherapee/RawTherapee/blob/dev/rtengine/ipvibrance.cc，第 64、99–110 行）。Photons 没有肤色保护，也没有分区阈值：一条连续斜率取代了三个经验分界。

取舍

两条滑杆、一个常数斜率，换来的是可复现：自然饱和度的增益只由 ss 决定。代价是它分不清「皮肤的红」和「夕阳的红」，两者在同一 ss 上拿到同一增益。RawTherapee 的肤色曲线就是为此存在的，代价是一张按色相索引的表，写错就是可见的边界。

还有一处得提：S3 的饱和与 S3.6 的饱和不是同一个量。前者乘 HSL 的 ss（显示码的距离），后者乘 OKLCh 的 CC（感知彩度）。同一个像素在两张卡上各 +50 不是 +100，这是有意的分工，不是漏改。

4.8 HSL 八色带与黑白混合（S3.6 / S3.4）

它解决什么问题

「只把天空的蓝压暗」需要一条按色相索引的通道；「把红苹果压成深灰、把蓝天提成浅灰」需要同一张索引表去定每个色相在灰里的分量。前者是 HSL 卡，后者是黑白混合，两者必须共用同一组色相中心，否则同一个「蓝」在两张卡上会落在不同位置。

亮度轴的定义是这里的关键。HSL 的 l=(mx+mn)/2l=(m_x+m_n)/2 是对交给它的那三个数取的，与光量无关：在线性光上，纯蓝与纯黄的 ll 都是 0.5，亮度却差 6.9×（0.0722 对 0.500）；在 OKLab 上这两个颜色读出 0.452 与 0.968（HSLBands.swift:18–:21、Stage.swift:95–:96）。这是 079 结论 4，也是八色带从 S3 搬进 S3.6 的全部理由。

算法

空间是 OKLCh。折叠矩阵不是 Ottosson 发表的那组 sRGB 字面量，而是用工作基色重新推导的：M1 · toXYZ(Rec.2020)，每行归一到和为 1（白必须折成 L=1,a=b=0L=1,a=b=0），九个结果字面量写死在 kernel 里（oklch_bands.metal:36–:40；推导在 Masks.swift:598–:611）。

[lms]=M1[rgb],[Lab]=M2[l1/3m1/3s1/3]\begin{bmatrix}l\\m\\s\end{bmatrix}=M_1\begin{bmatrix}r\\g\\b\end{bmatrix}, \qquad \begin{bmatrix}L\\a\\b\end{bmatrix}=M_2 \begin{bmatrix}l^{1/3}\\m^{1/3}\\s^{1/3}\end{bmatrix}

M2M_2 是发表的 OKLab 矩阵（oklch_bands.metal:42–:44）。逆向是 M2−1M_2^{-1}、立方、M1−1M_1^{-1}，同样十八个字面量逐个写出（:56–:62）。色相与彩度：

C=a2+b2,h=180πatan2⁡(b,a)(mod360)C=\sqrt{a^2+b^2},\qquad h=\frac{180}{\pi}\operatorname{atan2}(b,a)\ \ (\mathrm{mod}\ 360)

中性门是必须的：折叠矩阵的行只在 10−1010^{-10} 的精度上求和为 1，一个数学上的灰会带着 C≈10−8C\approx10^{-8} 和一个任意角度回来，足够让它走过一遍转换、改掉最后一位。所以门在 10−610^{-6} 处恰好为 0，在 0.02 处为 1，中间是 smoothstep（oklch_bands.metal:81–:83）。

八条带各自的权重是一个局部支撑的三次多项式，rr 是该侧到邻中心的角距：

wi=1−t2(3−2t),t=|Δhi|ri,|Δhi|≥ri⇒wi=0w_i=1-t^2(3-2t),\qquad t=\frac{\lvert \Delta h_i\rvert}{r_i},\qquad \lvert\Delta h_i\rvert\ge r_i\Rightarrow w_i=0

（oklch_bands.metal:68–:73）。rr 不是八分之一圈，是到那一侧邻居的实际间距（HSLBands.swift:150–:159）：中心在 OKLCh 角度上并不等距，红 24.78°、橙 80.03°、黄 109.42°、绿 143.00°、青 195.00°、蓝 274.46°、紫 320.84°、品红 335.01°，相邻间距从 14.17°（紫→品红）到 79.46°（青→蓝）（HSLBands.swift:81–:90）。每个间隙由两侧的带共同覆盖，两边的权重是一对互补的 smoothstep（S(t)+S(1−t)=1S(t)+S(1-t)=1），所以 ∑wi=1\sum w_i=1 在每一个色相上都成立，缝上也是。除法仍然无条件做一次（s3_6_hsl.metal:160），那是把「恰好为 1」变成保证，不是修正。

三条滑杆：色相是偏移，饱和乘 CC，亮度乘 LL：

h′=h+0.3sh,C′=C(1+ss100),L′=L⋅2sl/100h'=h+0.3\,s_h,\qquad C'=C\Bigl(1+\frac{s_s}{100}\Bigr),\qquad L'=L\cdot 2^{s_l/100}

（s3_6_hsl.metal:170–:172）。±100\pm100 对应 ±30°\pm30°、×2\times2 / ×0\times0、±1\pm1 档感知亮度。第九个选择器「全局」是同一组三轴，加在带偏移之后，单位相同；它的色相与饱和走同一道中性门，明度不走（灰没有色相可转，但可以被提亮）（:116–:118）。它由编译期模板参数分成两个 kernel 入口，所以 076 的默认实例里根本没有那段算术（:46–:49、:181–:195）。

黑白混合在同一张表上只读一个数（HSLBand.mix，主机侧塞进 .v.x：RenderGraph.swift:6575）：

g=smoothstep(10−6,0.02,C),m=∑iwimi∑iwig,grey=L3⋅2m/100g=\mathrm{smoothstep}(10^{-6},\,0.02,\,C),\qquad m=\frac{\sum_i w_i\,m_i}{\sum_i w_i}\,g,\qquad \mathrm{grey}=L^3\cdot 2^{m/100}

（s3_4_bw.metal:90、:112、:118、:120、:145）。三个量分开说：

  • L3L^3 而不是 LL。 灰要的是「这个感知亮度在线性光里的值」，而 M2−1M1−1M_2^{-1}M_1^{-1} 的三行和为 1，所以 OKLCh−1(L,0,h)\mathrm{OKLCh}^{-1}(L,0,h) 恰好是 L3L^3 的三个相同分量。写成三次乘法而不走矩阵，是为了三个通道逐位相同，不是在容差内相同（:139–:146）。
  • ±1\pm1 档线性光，不是感知亮度。 混合说的是「这个颜色在相纸里沉积多少光」，是密度，密度是线性的；S3.6 的亮度说的是「这个颜色看起来多亮」，两者差 8 倍光量。混用会让「绿 +100」把一片中调的叶子推成高光（s3_4_bw.metal:28–:33）。
  • 乘性，所以黑仍是黑。 0⋅2k=00\cdot 2^k=0：一条影调里没有的颜色，滑杆抬不动它。

转换本身不看混合值：开关打开、八个 mix 全 0，画面照样变灰，灰落在像素自己的 LL 上（:40–:44）。stage 是条件的，只有开关为真才进链（EditModel.swift:421），所以彩色文档根本没编码这个 pass。

参数与范围

范围与默认全部来自 HSLBand（EditModel.swift:2215–:2226）与 ColorGroup（:2061–:2087）：

实现

Kernels/oklch_bands.metal 是唯一的几何定义：中心、间距、权重函数、中性门，全部一份，由 S3.6 与 S3.4 两个 kernel 各自 #include（oklch_bands.metal:3–:10）。CPU 侧 HSLBands 是同一份代数在 Double 上的参考实现，HSLTests 拿两者对跑（HSLBands.swift:9–:13）。

中心不是手写的度数，是用 Lightroom 的 HSL 角度反算出来的：取 hsl(0/30/60/120/180/240/285/315, 0.85, 0.5) 这八个物理颜色，转到工作基色，再量它们的 OKLCh 色相（HSLBands.swift:136–:145）。所以「红」这个带作用的是那只红苹果，不是 sRGB 色环上的 0°。

上传一份八元结构体数组，每个元素带三轴值与中心、两侧间距（RenderGraph.swift:6547–:6563）。S3.4 用同一张表，只把 mix 放在 .v.x、其余两轴置 0（:6569–:6584）。

顺序上 S3.4 在 S3.6 之前（Stage.swift:195），不是随便排的：黑白写出的灰 C=0C=0，S3.6 的中性门会让它整段直写，两个 stage 的唯一交互因此是「下游自动失效」，而不是「下游再算一遍」。

开源对照

  • darktable · colorzones.c：最接近的邻居，八个控制节点落在 Lab/LCh 的色相轴上，本质是一条色相曲线（https://github.com/darktable-org/darktable/blob/master/src/iop/colorzones.c）。差别在归一化：076 之前 Photons 的旧方案只在八顶帐篷之和超过 1 时才归一，于是绿 +100 在自己中心给出 100、在 90°/150° 只剩 25.93，形成 4 倍波纹（HSLBands.swift:99–:101、s3_6_hsl.metal:20–:26）。现在是构造性的单位和。
  • RawTherapee · HSV Equalizer（improcfun.cc）：076 搬离的就是这种构造，在 HSV 里对 H / S / V 各挂一条 FlatCurve，按色相查表（https://github.com/RawTherapee/RawTherapee/blob/dev/rtengine/improcfun.cc，第 2162–2193 行）。差别是空间与门：HSV 是设备空间的 ll，没有色度门，灰的色相是任意的，把它当索引去查曲线，结果取决于浮点噪声。
  • darktable · colorbalancergb.c 的 hue/chroma 轴：绝对色相角加彩度乘数，没有「带」的概念。一串叠加的绝对值没有「所有带同值 = 全局同值」这个性质，局部支撑的带权重有。 https://github.com/darktable-org/darktable/blob/master/src/iop/colorbalancergb.c

取舍

八段局部支撑换来两件事：可预测（一个带在自己中心恰好给 100）与可加（八个带同值时处处相同）。代价是它分不清「高光里的蓝」和「阴影里的蓝」，那是亮度轴的事，归 S3.8，不归这里。

黑白混合挂在同一张表上，省掉第二套色相中心，代价是它只能在开关打开时读：关掉后 mix 仍留在文档里但不渲染（EditModel.swift:2223–:2226），切回彩色因此逐位可复现。

4.9 点颜色与三向色彩分级（S3.6b / S3.8）

它解决什么问题

八色带只认色相，一片枯草和一块肤色在同一个橙带里会得到同一处理。人眼区分「同一材质」靠三件事一起：亮度接近、色度接近、色相接近。点颜色要的是一个区域，围绕一个采样点的盒子，不是一条色相线。三向分级要的是另一个维度：同一个颜色在阴影里该偏冷、在高光里该偏暖，跟它是什么颜色无关。

算法

点颜色的窗口建在 OKLCh 上（285），三条轴各是一个「平台 + 肩」的软盒：色相是角度（折到 [−180°,180°)[-180°,180°)），色度是相对采样色的比例，亮度是 OKLab 的 LL：

wi=wh(Δhi)⋅wc(ΔCi)⋅wl(ΔLi)⋅[Cpx≥12c0]w_i=w_h(\Delta h_i)\cdot w_c(\Delta C_i)\cdot w_l(\Delta L_i)\cdot[\ C_{\text{px}}\ge\tfrac12 c_0\ ]

waxis=1−smoothstep(daxis,daxis+saxis,|xpx−xsample|)w_{\text{axis}}=1-\mathrm{smoothstep}\bigl(d_{\text{axis}},\ d_{\text{axis}}+s_{\text{axis}},\ |x_{\text{px}}-x_{\text{sample}}|\bigr)

（s3_6b_point_colour.metal:10、PointColor.swift:249。）dd 是平台半宽、s=12d⋅过渡s=\tfrac12 d\cdot\text{过渡} 是肩宽，所以默认（范围 30、过渡 30）下盒子在边界上恰好归零、C1C^1：

轴 平台 dd（范围 30） 满宽（归零处）
色相 ±10° ±15°
色度 采样色的 30 %，夹在 0.02…0.12 再一半
亮度 LL ±0.08 ±0.12

（PointColor.swift:58、:60、:63、:66、:68。）色相平台 10° 正是用户口径里「两种不同颜色」的最小间距 15° 的一半，肩把边界推到 15°，于是两色相差 15° 时默认窗口里恰好零权重（PointColor.swift:56）。色度用相对容差不只是省一个单位：暗部的绝对色度本来就小，固定容差会把不同材质的地面色一起抓进来；0.02 的下限保证 范围 = 0 时仍是一个点，不是负宽度。

另有一道硬地板：像素自身的 OKLab CC 低于 0.5c0=0.010.5\,c_0=0.01 时权重直接为 0（s3_6b_point_colour.metal:12）。灰因此逐位不变，接近灰的渐变也不会被误染。

最多八个采样色，所有权重都在阶段输入上求一次，再除以 max⁡(1,∑w)\max(1,\sum w)。这也是 285 改掉的一处：140 让每个采样色看前一个的输出，于是数组顺序会改变结果。现在两个满权重盒子分摊一个像素，而不是把它移动两次；色相肩还会被最近邻的角距在主机侧预先截短（s3_6b_point_colour.metal:20、PointColor.swift:206）。三个调整量与 HSL 卡同单位：

H+=wah0.3,C←max⁡(C(1+was100),0),L←L⋅2wal/100H\mathrel{+}=w\,a_h\,0.3,\qquad C\leftarrow\max\Bigl(C\bigl(1+w\tfrac{a_s}{100}\bigr),0\Bigr),\qquad L\leftarrow L\cdot 2^{\,w a_l/100}

（s3_6b_point_colour.metal:130–:132）。每个量都乘 ww，所以在肩上三条一起归零；色相旋转可能把颜色转出工作基色，负通道在出口一次性夹到 0，顶部不夹，显示域的高光保留它的 headroom，S4 才是唯一的夹取点（:137）。

三向分级用 S2 的亮度窗口决定「哪个轮子管这个像素」：

wsh=1−smoothstep(−5.9,−3.9,L),whi=smoothstep(−3.2,−1.2,L),wmid=1−wsh−whiw_{sh}=1-\mathrm{smoothstep}(-5.9,-3.9,L),\qquad w_{hi}=\mathrm{smoothstep}(-3.2,-1.2,L),\qquad w_{mid}=1-w_{sh}-w_{hi}

（tone_shape.metal:53–:57、s3_8_grade.metal:77–:81），其中 L=log⁡2YL=\log_2 Y，YY 按工作基色的权重求（:54）。两个窗口不重叠（−3.9<−3.2-3.9<-3.2），第三个数是余量，所以三者和恒为 1，这个 stage 也没有自己的窗口表。

参数先混后算，这样中性轮在自己区域里给出恰好零：

δh=0.3∑iwihi,κ=1+1100∑iwisi,δl=1100∑iwili\delta h=0.3\sum_i w_i h_i,\qquad \kappa=1+\frac{1}{100}\sum_i w_i s_i,\qquad \delta l=\frac{1}{100}\sum_i w_i l_i

（s3_8_grade.metal:107–:113）。然后：

v1=OKLCh−1(L,κC,h+δh⋅g),v2=v1⋅clamp(YinY(v1),0.125,8),out=v2⋅2δlv_1=\mathrm{OKLCh}^{-1}\bigl(L,\ \kappa C,\ h+\delta h\cdot g\bigr),\qquad v_2=v_1\cdot\mathrm{clamp}\Bigl(\frac{Y_{\mathrm{in}}}{Y(v_1)},\ 0.125,\ 8\Bigr),\qquad \mathrm{out}=v_2\cdot 2^{\delta l}

（:136–:138、:165–:169、:172–:174）。三步各有理由：

  • 色相旋转在 LL 与 CC 不动的前提下做，亮度不跟着动；饱和改 CC 会改 YY（同 LL 下更鲜艳的像素亮度不同），所以第三步把 YY 乘回输入值。这个恢复是一次均匀增益，而均匀增益不会移动 OKLCh 色相：折叠对 RGB 线性，立方根把增益变成 (ℓ,m,s)(\ell,m,s) 上的标量，(L,a,b)(L,a,b) 同乘 g1/3g^{1/3}，atan2⁡(b,a)\operatorname{atan2}(b,a) 不变（ColorGrade.swift:33–:38）。「饱和不动色相」因此是算术性质，不是容差。
  • 工作基色装不下的彩度会回来一个负通道，硬剪会转色相（阴影片上实测 8.4°）并丢掉刚恢复的亮度，所以要缩短这次移动：在输入彩度与请求彩度之间二分六步，停在装得下的最宽处（s3_8_grade.metal:152–:160）。
  • 亮度是纯增益 2δl2^{\delta l}，±100\pm100 就是该区域 ±1\pm1 档光，与曝光同一个单位，档（ColorGrade.swift:64–:65）。

实现

Sources/PhotonsCore/Kernels/s3_6b_point_colour.metal 与 Sources/PhotonsCore/Kernels/s3_8_grade.metal，两个全分辨率 pass，都在 S3.6 之后、S3.9 之前（Stage.swift:195）。两者都带同样的三道早退：空内容窗口、alpha 0、内容矩形之外。

点颜色的 kernel 是两趟：第一趟在输入像素上把八个权重全部算出来并求和，第二遍按 w/max⁡(1,∑w)w/\max(1,\sum w) 依次施加三个调整（s3_6b_point_colour.metal:97、:120）。285 让结果与数组顺序无关的地方就在这里，140 的时候第二个采样色看到的是第一个的输出。

分级的主机侧把「混参数」定义成 Effective（色相度、彩度乘数、光档），顺序与 kernel 一致：先混、再转换、再恢复亮度、再加增益（ColorGrade.swift:110–:134）。

还有一处要留意： Kernels/tone_shape.metal 里现在有两个窗口函数：074 R2 的两窗 region_weights（:53）与 085 的三窗链 region_weights3（:98），S2 的全局段用后者，分级仍 include 前者（s3_8_grade.metal:10–:16）。两套在 −3.9-3.9 以下、−1.2-1.2 以上一致，中间的过渡不同；ColorGrade.swift:45–:52 的注释还写着「S2 自己的窗口」，严格说只对 074 成立。改窗口时两处必须一起改，否则「高光」在两张卡上会重新变成两个区域。

开源对照

  • darktable · colorbalancergb.c：三只轮子加一个全局段，工作在 Filmlight Ych，每只轮存绝对色相角（https://github.com/darktable-org/darktable/blob/master/src/iop/colorbalancergb.c）。Photons 存的是偏移：交叉淡化时偏移是普通数，直接线性插值即可；绝对角需要圆环插值（350° 与 10° 相差 20°，不是 340°），而且「阴影是橙色」会变成「把所有阴影像素旋到橙色」，抹掉画面自己的颜色差异（EditModel.swift:2280–:2061）。
  • RawTherapee · Color Toning（improcfun.cc）：阴影/中间调/高光各三个 RGB 数，外加饱和度保护与一条强度曲线（https://github.com/RawTherapee/RawTherapee/blob/dev/rtengine/improcfun.cc，第 2281–2296 行）。它直接加在通道上，所以会同时改亮度与色相；Photons 先转色相、再恢复 YY、最后才乘亮度，三个量互不串。
  • LightZone · ColorBalanceOperation.java：三条互补轴（Cyan-Red / Magenta-Green / Yellow-Blue）加一个 midpoint，Highlights / Midtones / Shadows 三个选项把 midpoint 设成 0.62 / 0.18 / 0.04，最后生成每通道一条 B 样条 LUT（https://github.com/ktgw0316/LightZone/blob/master/lightcrafts/src/main/java/com/lightcrafts/model/ImageEditor/ColorBalanceOperation.java，第 83–140 行）。差别是维度：它一次只作用一个影调档，靠通道加减；Photons 三个档同时按权重混合，旋转的是 OKLCh 色相。

取舍

点颜色的盒子是矩形：三个轴独立，所以它抓不住「同一色相、不同明度」斜着穿过盒子的颜色（一条从亮到暗的渐变会有一半在盒外）。换成椭球能贴合得更好，但每个采样色要多存一个方向，八个的上限立刻变成负担。285 把轴从 YCbCr 换成 OKLCh 之后，盒子仍然是一个盒子，变的是度量，不是形状。

色度轴是相对采样色的（30 % 的自身 C），代价是一个很暗的采样色窗口也小：同材质在阴影里的容差比高光窄。这是有意的，暗部的绝对色度本来就小，固定容差会把不同材质一起抓进来。

这套系统按「一个维度一个 stage」组织，每个 stage 只有一个划分；代价是组合靠链序，先黑白再色带再分级，顺序变了结果就变，而链序不开放给用户。

分级的窗口只有一套，所以 18 % 灰（码 118）读作 −2.44-2.44 EV，落在 (0,0.70,0.30)(0,\ 0.70,\ 0.30)：中间调轮占七成，高光轮已经开始碰它（EditModel.swift:2352–:2353）。这是一张表的代价，也是「高光」这个滑杆自 074 R2 起就有的同一个重叠。

校准（CalibrationGroup，七个 ±100 的数）在 S1 的线性光上做矩阵，改的是「哪个通道算红」，不在这一章展开（EditModel.swift:2871、:388）。
