## 2 为什么会长成这样（不是设计出来的）

只有 loupe 同时握有三样东西，而测量、门、上屏判断都要它们：
1. **屏幕上那一帧的像素与事实**：`frameState.image` / `.graph` / `.capabilities` / `.scale` / `.graphPhoto`；
2. **队列归属**：哪个开发在飞、哪个帧是延后的（`editInFlight` / `viewInFlight` / `renderQueue`）；
3. **会话与文档写回**：`CatalogSession` 的编辑、历史、脏标记。

Core 里只有**求解器**（`AutoColor` / `AutoLight` / `AutoCropSolver` / `DecoderAutoVersion`），它们不知道哪一帧在屏幕上。
所以「求解器在 Core，测量与写回在 loupe」本身是对的，错的是**它们全都住在同一个类里**。

## 3 拆分原则（每一单都适用）

1. **纯搬家**：新文件收的是原样搬过去的代码。允许的新增只有 ① 服务自己的 `init`；
   ② loupe 上的**转发属性/方法**（同名同签名，测试与调用点一个字都不用改）；
   ③ 一个最小的事实值类型（如 `AutoAdjustService.Frame`），只在搬不动的边界上用。
2. **零行为变化**：`git diff` 里不出现新的分支、容差、常量、时序；搬走的注释原样搬走。
3. **判据 = 既有套件逐条计数不变**：每单在规格里点名自己的套件集合，要求「每一条用例的名字与 passed/failed 与基线逐条相同」。
4. **`*ForTesting` 一律保留**：测试是直接调 loupe 的，所以搬到服务上的 seam 必须在 loupe 上留同名转发
   （`var lastAutoColorMetricsForTesting { service.last… }`）。这条是纯搬家可验证的关键。
5. **一次一单**：一单合完再开下一单，避免两个 lane 同时搬同一批行（`main` 一次只前进一单）。

## 5 验收口径（每单一样）

- 该单点名的套件：**逐条用例名 + passed/failed 与基线相同**（基线在改码前先跑一遍并报数）；
- `LoupeController` 行数必须**减少**（报前后行数），新文件行数 ≤ 搬走的行数 + 40（转发与 init）；
- `grep` 校验：搬走的 `*ForTesting` 名字在 loupe 上仍可编译访问（有转发）；
- 反向门：至少一条——把某处转发改成「直接读服务」之外的行为改动（例如丢掉 448 门的 `queuePendingAuto`），
  点名的那条用例必须红；还原后绿。

## 6 不做的

- 不重命名任何公开 API、不动 Xcode/SwiftPM 结构（`Package.swift` 一字不改）。
- 不改时序、不改容差、不顺手修 bug —— 搬完再修，修是另一单。
- 不引入新的第三方依赖、不引入 Combine/async 流。
