# 3 处理架构：域、顺序、契约

第 2 章讲像素怎么到屏幕上。这一章讲**每个参数为什么在那个位置**。先给三个域的定义，再给一张全参数归属表，然后解释排序的八条判据、局部调整为什么横跨两个域，以及中性零变化这条契约是怎么被工程化的。最后一节讲版本与迁移。

## 3.1 三个域

| 域 | 量 | 能不能大于 1 | 典型操作 | 判据 |
|---|---|---|---|---|
| **RAW 解码域** | 相机样本，Apple 解释 | 是（HDR 余量） | 去马赛克、白平衡、机身降噪、镜头校正 | 需要马赛克或厂商模型的事，只能在这里做 |
| **场景线性域** | 线性光，`1` = SDR 白 | 是（最高约 16×） | 黑电平、曝光、端点、曲线、去雾、暗角、校准矩阵 | 操作是**光的乘加**，且必须在压缩之前 |
| **显示参考域** | 显示码，`0…1` | 否 | 三段影调、对比、饱和、HSL、分级、细节、颗粒 | 操作的对象是「显示出来的样子」，或依赖色调映射后的亮度窗口 |

域的边界不看审美，看信息还在不在。S2 把场景压进 `0…1`，被压掉的高光就再也拿不回来。反过来，在线性域对已经显示的像素做「局部对比」，也没有可用的亮度参照。第三、四章的每个反例都能归到这两句话之一。

## 3.3 顺序的八条判据

① 几何最先（S0）。裁剪、旋转、透视、镜头 warp 都改像素网格本身。后面所有按像素做的运算都拿它的输出当基准：蒙版坐标、暗角半径、锐化半径。几何要是放到后面，每一步都得重新解释一次坐标。

② 修复先于一切，包括几何（249）。修复画笔修的是画面，不是调色。它作用在 S1 的**源像素**上，所以跑在 S0 之前：一处修补跟着照片走，裁切、拉直、90° 转过来之后还是同一块像素。它也不能等到曲线和色调映射之后，否则曲线会把补丁放大成一块看得见的斑（`Sources/PhotonsCore/Stage.swift:24`）。代价是补丁的落点得在源像素坐标里算，也就是要做逆变换，249 一并做了。

③ 曲线在色调映射之前（S1.7）。030 把曲线从 S3 挪到 S1.7。曲线现在工作在 HDR 轴上，`+4 EV` 的高光在进 S2 之前就按用户的意图弯过了。放到 S2 之后，用户只能弯 S2 已经压过的数据，「高光」滑杆和曲线上的高光段会互相打架（`Stage.swift:37`）。

④ 对比在色调映射之后（S2.5），且与曝光可交换。159 之前对比在 S1.8，场景线性、锚点固定。实测 `曝光 × 对比` 不可交换：同一个对比值在 E0 与 E+2 下给出的 p50 增益不同（0.666 vs 2.695），74 % 的像素改变方向。228 把它恢复成显示域的**增益域幂律**：增益从「除掉曝光的亮度」里算出来，再乘回像素，于是 $\mathrm{render}(E)=2^E\mathrm{render}(0)$ 精确成立（`Sources/PhotonsCore/GlobalContrast.swift:8`、`Sources/PhotonsCore/Stage.swift:188`）。

⑤ 色彩在显示域（S3 之后）。饱和与 HSL 的对象是「看起来的颜色」。HSL 曾放在线性域，纯蓝与纯黄的 `l` 都是 0.5，两者的亮度差却有 6.9×（`Stage.swift:90`）。搬到 OKLCh 的显示域之后，`L` 才与感知亮度对应。

⑥ 去雾在光域（S1.9）。去雾模型 `J = (I − A(1 − t))/t` 里的 `A` 是空气光，是场景里的一个光量。117 之前它在显示域、`A` 固定为 1，于是 `I > 1` 的高光越去雾越亮（`Stage.swift:56`）。

⑦ 暗角在光域、且在色调映射之前（S3c）。暗角是照度衰减的**校正**，乘的是光，不是显示码。放到 S2 之后，暗角就变成了一个「暗部窗口」操作（`Stage.swift:151`）。它还得到去雾之后：不然暗角的衰减会被暗通道当成雾幕。

⑧ 细节与锐化在显示域、色彩之后、颗粒之前。纹理、清晰度、锐化都是「成品图上的细节」，半径按内容像素定义。所以 1:1 与 25 % 预览锐化的是同一处细节（`Sources/PhotonsCore/EditModel.swift:2631`）。颗粒放在最后：它盖在已经完成的画面上，之后只剩 S4 编码（`Stage.swift:155`）。

## 3.4 局部调整：一张蒙版横跨两个域

蒙版本身只产出一张覆盖率图（S1.5 图集），域不属于它。域属于被蒙版加权的那次运算。056 按域把局部量拆开：

| 量 | 阶段 | 域 | 理由 |
|---|---|---|---|
| `exposure`、`temperature/tint`、`highlights/shadows/whites/blacks` | S1.6 | 场景线性 | 是光量，且要在 S2 压缩之前 |
| `hue`、`saturation` | S3.5 | 显示参考 | 与全局 S3 同一算子，全画布蒙版必须等于全局滑杆 |
| `contrast` | S2.5 | 显示参考 | 159：与全局对比同一算子、同一域 |
| `texture`、`sharpen` | S3.9 | 显示参考 | 181：与全局纹理/锐化同一带、同一 ε |

`amount` 是 0…100 的整体权重，`opacity` 是覆盖率的整体缩放。两者都在各自的阶段里乘进权重。`feather` 的半径用**短边百分比**表达，所以任何画布尺寸下物理宽度都一样（`Masks.swift`、`docs/architecture-decisions.md §11.11`）。

两个工程细节：

- **图集只依赖形状，不依赖调整。** 一张蒙版改曝光不会重建图集（S1.5 的键不含调整）。拖动局部滑杆之所以只重跑一个 pass，原因就在这里（`Masks.swift:30`）。
- **tile 是成本旋钮，不是质量旋钮。** 蒙版覆盖不到一半画布时按 tile 重算，两种分派的输出必须逐字节相同（`RenderGraph.swift:137`）。

## 3.5 中性零变化：谓词，而不是乘法

每一条「没碰过就等于没发生」的承诺，都落在同一个机制上：条件 stage 的**谓词**。谓词看值，不看对象是否存在。

| 阶段 | 谓词 | 位置 |
|---|---|---|
| S1.5 / S1.6 | `masks` 非空 | `Stage.swift:221` |
| S1.9-heal | 有修复点 | `Sources/PhotonsCore/Stage.swift:222` |
| S1.9-dehaze | `dehaze ≠ 0` | `:230` |
| S2.5 | 全局 `contrast ≠ 0`，或某个蒙版的 `contrast ≠ 0` | `Stage.swift:291` |
| S3.4 | 黑白开关为真 | `:223` |
| S3.5 | 某蒙版带色相或饱和 | `:224` |
| S3.6 | 24 个 HSL 数任一非零 | `EditModel.swift:2163` |
| S3.6b | 至少一个采样色且被调整 | `:2173` |
| S3.8 | 九个分级数为任一非零 | `EditModel.swift:427` |
| S3.9 | 纹理/清晰度/去噪/去彩噪任一非零 | `:2523` |
| S3.10 | `amount > 0` | `EditModel.swift:406` |
| S3.7 | `grain > 0` | `:2517` |

谓词为假时，这个阶段的链接**整条不写**。这里没有「写一个中性值」这回事，键链和阶段列表都退化成没有这个功能时的样子。老文档的 trace、键、像素之所以能同时逐字节复现，原因就是这个（`Stage.swift:15`）。

文档层面还有一条同源规则：中性值**不落盘**。`blackOffset = 0`、`quarterTurns = 0`、`blackAndWhite = false`、全零的分级组、全零的锐化组，JSON 里都不写键。读回来是默认值，再写出去逐字节相同（`EditModel.swift:1622`、`:2129`、`:2384`）。

## 3.6 五个顺序陷阱

这几条都不是抽象风险，每条都有实测症状和对应的修正。

**① 曝光 × 对比不可交换（142 → 159）。** 旧实现把对比锚在场景线性的绝对亮度上。同一张图先加曝光再加对比，和先对比再加曝光，出来的不是同一张。p50 增益在 E0 与 E+2 下相差 4 倍，74 % 的像素方向相反。修正：对比改成显示域的残差增益，不再有绝对锚点（`Stage.swift:42`）。

**② HSL 在线性域（079）。** 纯蓝与纯黄在线性域的 `l` 都是 0.5，感知亮度却差 6.9×。拖动「蓝色明度」会把天空拖成灰。修正：八色带搬到显示域的 OKLCh，S3 只留自然饱和/饱和（`Stage.swift:90`、`:94`）。

**③ 去雾在显示域（117）。** `A = 1` 的显示域版本对 `I > 1` 的样本**加光**：去雾越强，高光越亮，天空先爆。修正：暗通道加实测 airlight，放在场景线性域做，`A` 由画面估计，负值只表示「把雾加回来」（`Stage.swift:56`）。

**④ 暗角在显示域（116）。** 暗角补偿的是照度衰减，乘在显示码上等于「把角落加点黑」，和曝光、对比的交互完全错位。修正：移到线性链末尾、S2 之前（`Stage.swift:151`）。

**⑤ 曲线在色调映射之后（030）。** 曲线只能弯 S2 已经压过的数据，`+4 EV` 的高光在曲线看到它之前就被当成「高光区」处理了。修正：曲线移到 S1.7，横轴换成直方图自己的轴（SDR 半加 `+0…+4 EV` 半），见 4.6（`Stage.swift:37`）。

## 3.7 解码域与 S1 的分工

白平衡是两段的：落定在解码域，拖动在 S1。文档里的 `temperature/tint` 不是 `nil` 时，写进 `CIRAWFilter.neutralTemperature/neutralTint`，解码器据此出图。所以它决定「哪张缓冲」，进的是解码键（`Sources/PhotonsCore/EditModel.swift:1521`、`Sources/PhotonsCore/RAWDecoder.swift:587`、`Sources/PhotonsCore/DecodeInputs.swift:84`）。`nil` 表示 as shot，这时**完全不碰 filter**：把读到的 as-shot 值再赋回去不是恒等，约 0.15 % / 0.40 % 的样本会移动（`docs/STATUS.md`）。默认像素逐字节不变，前提就在这里。

拖动期间由 S1 的 3×3 顶上。解码一次要数百毫秒，拖滑杆不可能每帧重解。`WhiteBalanceEstimate` 因此给出一个**锚点相对**的矩阵 `M(document)·M(buffer)⁻¹`：请求的 `(K, tint)` 是 CIE 1960 uv 上 Planckian 轨迹的一点加垂直 tint 位移（0.000343 uv/单位，按解码器实测标定），uv → XYZ，Bradford 适配到工作基色的 D65 白点，再折成工作基色里的完整 3×3（`Sources/PhotonsCore/WhiteBalanceEstimate.swift:297`、`:428`）。195 之前这里只有三个通道数（von Kries 对角），实测与解码器的完整矩阵在 3200 K 差 97 码。现在用完整积，外推失控时退回对角（`Sources/PhotonsCore/WhiteBalanceEstimate.swift:496`）。所以约定是「预览是近似、落定是真值」：两边一致的是请求的白点，不是实现。

镜头校正是文件事实。DNG 有三个不同平面、或 RW2 有可用剖面时，Photons 关掉 Apple 的校正，自己在 S0 做 warp；否则用 Apple 的。判断依据随文件走（`RenderInput.lensProfile`），也进解码键，因为「哪套校正跑过」决定了像素（`Sources/PhotonsCore/RenderGraph.swift:34`、`Sources/PhotonsCore/LinearImageStore.swift:41`）。

降噪有两套，别混。`DetailGroup.noiseLuminance/Color` 是解码参数，走 `CIRAWFilter` 的机身降噪，改它要重新解码。`EffectsGroup.nonBayerLuminanceNR/ColorNR` 是 S3.9 的显示域降噪，引导滤波残差加 OKLab 色度抑制，可以实时预览。两组数在面板上是不同的卡，在文档里是不同的组，在键里也是不同的阶段（`Sources/PhotonsCore/EditModel.swift:2639`、`:2500`）。

## 3.8 版本、格式与迁移

| 机制 | 现在是什么 | 变了会怎样 |
|---|---|---|
| `processVersion` | 2：曲线从 S3 搬到 S1.7 的那次语义变更 | 旧文档保留控制点，但渲染不同；这是**声明过的迁移**，不是 bug（`Sources/PhotonsCore/EditModel.swift:144`） |
| 曲线格式块 | `version 2`、`type: double`、`max: 2`、`domain: "hdr"` | 读到不认识的版本不猜：整条曲线退回恒等，其余字段照常加载，并留一条 `decodeWarnings`（`Sources/PhotonsCore/EditModel.swift:1753`、`:1857`） |
| `DecodeRecipe` | `v3-lens` | 配方变更意味着**旧缓冲不可复用**（镜像 bug、RW2 warp），磁盘缓存靠它失效（`LinearImageStore.swift:16`） |
| schema | 13：11 删掉绝对的 `blackLevel/whiteLevel`、只留 `blackOffset`；12 加透视/旋正字段；13 加修复点 | 老文档带着旧键也能读（未知键被忽略），重新保存会写成新 schema（`Sources/PhotonsCore/EditModel.swift:132`） |
| 未知键 | 一律忽略，不报错 | 手写/未来文档不会让整张照片打不开；坏值按默认值处理（`AnyCodingKey.val`，`EditModel.swift:3109`） |
